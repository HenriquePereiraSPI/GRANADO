Referência de APIs

Catálogo das APIs de servidor do Granado expostas no Apriso (prefixo GRD_API_). Cada API recebe um payload JSON e retorna um envelope padrão com Success, Message e Data. A documentação abaixo descreve, por API, os campos de entrada, os de saída e exemplos prontos para teste.

$Context

_BestPractices · padrões e boas práticas de uso do Apriso.

Para utilizar o $Context, o Apriso injeta essa variável dentro da aba HTML, e podemos pegá-la e injetá-la dentro de uma variável da página para conseguirmos utilizá-la na aba JavaScript: 

<main>
  <h1> </h1>
  <span> </span>
  ...
</main>
<script>
(function () {
    function init() {
        if (typeof $Context !== 'undefined') {
            window.AprisoContext = $Context;
        }

        //funções que irão ser executadas ao carregar a pagina
          initializeEvents();
          initializeStatics();
    }

    if (document.readyState === 'loading') {
        document.addEventListener('DOMContentLoaded', init);
    } else {
        init();
    }
})();
</script>

Responsividade

_BestPractices · padrões e boas práticas de uso do Apriso.

Por padrão, sempre que houver necessidade de criar uma página responsiva, dividimos o layout entre WEB e MOBILE. Veja o que vai em cada aba do Apriso:

Na aba HTML vão os dois blocos do layout (WEB e MOBILE) e, no fim, o script de inicialização que chama initResponsiveLayout(): 

<main>

<!-- ============================================================ -->
<!-- ============================================================ -->
<!-- ========================== WEB ============================= -->
<!-- ============================================================ -->
<!-- ============================================================ -->
<div id="NOME_DA_SUA_PAGINA_WEB">
  //ELEMENTOS DO LAYOUT WEB
</div>

<!-- ============================================================ -->
<!-- ============================================================ -->
<!-- ========================== MOBILE ============================ -->
<!-- ============================================================ -->
<!-- ============================================================ -->
<div id="NOME_DA_SUA_PAGINA_MOBILE">
  //ELEMENTOS DO LAYOUT MOBILE
</div>
</main>

⚠ Atenção · evite usar IDs com grande possibilidade de conflitarem com outras partes do layout — por exemplo HEADER_WEB ou SIDEBAR_WEB. Prefira nomes específicos da sua página.

⚠ Atenção · não utilize o mesmo ID nos dois layouts (WEB e MOBILE) — eles se conflitam. A ideia é que cada layout seja único.

Exemplo: dentro do layout MOBILE você tem um <span id="span-1">; se no layout WEB você também tiver um <span id="span-1">, eles vão se conflitar. Nesse caso, a melhor prática é concatenar com WEB ou MOBILE — por exemplo span-1-mobile e span-1-web. 

<script>
(function () {
    function init() {
        if (typeof $Context !== 'undefined') {
            window.AprisoContext = $Context;
        }

        initResponsiveLayout();
    }

    if (document.readyState === 'loading') {
        document.addEventListener('DOMContentLoaded', init);
    } else {
        init();
    }
})();
</script>

Na aba JavaScript ficam as funções que alternam os blocos conforme o breakpoint (só disparam ao cruzar os 768px): 

function initResponsiveLayout() {

    var MOBILE_QUERY = "(max-width: 768px)";
    var mq = window.matchMedia(MOBILE_QUERY);

    updateResponsiveLayout(mq.matches);

    // dispara só ao cruzar o breakpoint
    mq.addEventListener("change", function (e) {

        updateResponsiveLayout(e.matches);
    });
}

function updateResponsiveLayout(isMobile) {

    document.getElementById("NOME_DA_SUA_PAGINA_WEB").style.display = isMobile ? "none" : "block";
    document.getElementById("NOME_DA_SUA_PAGINA_MOBILE").style.display = isMobile ? "block" : "none";

}

WebComponent

_BestPractices · padrões e boas práticas de uso do Apriso.

Como criar, instalar e usar um web component do Spi seguindo os padrões do projeto.

Arquitetura

  • Light DOM — sem Shadow DOM; o componente escreve em this.innerHTML.
  • Zero stylesheet injetado — toda estilização é inline (style="..."). Pseudo-classes (:hover, foco) via JS, não CSS.
  • Sem var(--x) dentro do componente — cores/medidas hardcoded como default; para customizar, exponha um atributo (ex.: color="#1C5C31") e o usuário pode passar var(--x) por ele.
  • Guarda de registro no topo: if (!customElements.get('spi-<nome>')) { ... }.

Estrutura do arquivo

  • Comentário-cabeçalho documentando: descrição, Atributos (todos opcionais, com default), Propriedades JS, Eventos, Métodos e um Exemplo (com a linha de import).
  • class SpiXxx extends HTMLElement com static get observedAttributes(), connectedCallback, disconnectedCallback, attributeChangedCallback, um _render()/_build() e helpers (_esc...).
  • Constantes no topo: paleta + const FONT = "'Poppins','DejaVu Sans',Arial,sans-serif".
  • No final: customElements.define('spi-<nome>', SpiXxx) e window.SpiXxx = SpiXxx.

API / dados

  • Props JS com getter/setter refletindo nos atributos; lazy-props no connectedCallback (captura valores setados antes do upgrade).
  • Dados complexos por propriedade (el.data = [...]) ou atributo como JSON string (setAttribute('data', JSON.stringify(...))). Selecione internos por data-role="...".
  • Eventos: this.dispatchEvent(new CustomEvent('nome', { bubbles: true, composed: true, detail })).

Estilo

  • Tipografia: Poppins para texto; Arial para números/códigos; tabelas e conteúdo misto em Arial.
  • Campos (input/text/dropdown/calendar) compartilham font-size:13px; line-height:1.4; padding:8px 12px; border:1px — altura igual por construção (sem height:100%).
  • Botões/ícones: box-sizing:border-box; margin:0; appearance:none; font-family:inherit + line-height explícito — o CSS global do Apriso sobrescreve <button>.

Host display & popups

  • Display do host sobreponível: this.style.display = this.style.display || 'inline-block' (widget inline) ou 'block' (seção). Elementos internos acompanham o display do host quando fizer sentido.
  • Popups/dropdowns: position:fixed (não absolute) com posição calculada no JS (getBoundingClientRect), p/ escapar do overflow/stacking dos containers do Apriso.

Responsividade & entrega

  • Se for responsivo: divida em blocos _WEB / _MOBILE alternados por JS num breakpoint (matchMedia("(max-width: 768px)")) — ver Responsividade.
  • Entregue um exemplo de uso com pelo menos 1 caso com JSON hardcoded direto no atributo (não só via setAttribute).

Esqueleto

/* __spi_guard__ */
if (!customElements.get('spi-exemplo')) {
  const SURFACE = '#FDFAF1';
  const BORDER  = '#D6CDA4';
  const VERDE   = '#1C5C31';
  const FONT    = "'Poppins','DejaVu Sans',Arial,sans-serif";

  class SpiExemplo extends HTMLElement {
    static get observedAttributes() { return ['label', 'color']; }

    connectedCallback() {
      // host inline por padrão (sobreponível pelo usuário)
      this.style.display = this.style.display || 'inline-block';
      this._render();
    }
    attributeChangedCallback() {
      if (this.isConnected) this._render();
    }

    // Propriedade JS refletida no atributo
    get color() { return this.getAttribute('color') || VERDE; }
    set color(v) { this.setAttribute('color', v); }

    _esc(s) {
      return (s == null ? '' : String(s)).replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;');
    }

    _render() {
      const label = this.getAttribute('label') || '';
      const color = this.color;
      this.innerHTML =
        '<span style="display:inline-flex;align-items:center;gap:8px;' +
        'border:1px solid ' + BORDER + ';border-radius:8px;padding:8px 12px;background:' + SURFACE + ';' +
        'font:13px/1.4 ' + FONT + ';color:' + color + '">' + this._esc(label) + '</span>';
    }
  }

  customElements.define('spi-exemplo', SpiExemplo);
  window.SpiExemplo = SpiExemplo;
}

GRD_API_AppointChecklist

Registra o apontamento de um checklist para uma ordem (WIP Order) em um recurso específico. Recebe a lista de checkpoints respondidos — cada um com seu valor (1 = conforme / 0 = não conforme) — e devolve o ID do apontamento gerado. Use ao concluir um checklist de turno, de POP ou de inspeção em processo.

Chamada

API GRD_API_AppointChecklist

Operação de servidor invocada com um corpo JSON. O retorno é sempre o envelope padrão (Success / Message / Data).

Inputs

Payload (antes do JSON.stringify)

Estrutura do objeto serializado em ChecklistPayload:

{
  "CheckListID": "100000002",
  "WIPOrderNo": "1000000001",
  "ResourceName": "100000032",
  "ResourceNameWorkcenter": "100000045",
  "CheckPoints": [
    { "CheckpointID": "100000002", "CheckpointValue": { "Checked": 1, "CustomValue": "1.500", "AditionalInformation": "Alguma informação do checklist" } },
    { "CheckpointID": "100000003", "CheckpointValue": { "Checked": 1, "CustomValue": "", "AditionalInformation": "" } },
    { "CheckpointID": "100000004", "CheckpointValue": { "Checked": 0, "CustomValue": "", "AditionalInformation": "" } },
    { "CheckpointID": "100000005", "CheckpointValue": { "Checked": 1, "CustomValue": "", "AditionalInformation": "" } }
  ]
}
const body = { ChecklistPayload: JSON.stringify(payload) };   // <- é isto que o endpoint recebe

Campos de entrada

Campo Tipo Obrigatório Descrição
ChecklistPayload string (JSON) Sim Payload do checklist serializado com JSON.stringify(...). Os campos abaixo compõem esse payload (antes de serializar).
CheckListID string Sim ID do checklist que está sendo apontado.
WIPOrderNo string Não Número da ordem (WIP Order) à qual o apontamento se vincula. Opcional — quando não for informar, envie "-1".
ResourceName string Não Identificador do recurso/equipamento onde o checklist foi executado. Opcional — quando não for informar, envie "-1".
ResourceNameWorkcenter string Não Identificador do workcenter (centro de trabalho) associado ao apontamento. Opcional — quando não for informar, envie "-1".
CheckPoints array<object> Sim Lista dos checkpoints respondidos. Cada item contém os campos abaixo.
CheckpointID string Sim ID do checkpoint dentro do checklist.
CheckpointValue object Sim Valor apontado para o checkpoint. Contém os campos abaixo.
Checked number (0 | 1) Sim Estado do checkpoint: 1 = conforme / sim, 0 = não conforme / não.
CustomValue string Não Valor customizado do checkpoint (ex.: medição "1.500"). Envie "" quando não houver valor.
AditionalInformation string Não Observação/texto livre associado ao apontamento do checkpoint. Envie "" quando não houver.

Outputs

Envelope de resposta (JSON):

{
  "Success": true,
  "Message": "Checkpoint apontamdo com sucesso.",
  "Data": "100000015"
}

Campos de saída

Campo Tipo Descrição
Success boolean Indica se o apontamento foi concluído com sucesso.
Message string Mensagem de retorno — confirmação em caso de sucesso ou detalhe do erro.
Data string ID do registro de apontamento gerado.

Notas

  • ChecklistPayload (string): o corpo tem só esse campo, e ele é o payload serializado — não envie o objeto direto. Use { ChecklistPayload: JSON.stringify(payload) }.
  • Envelope padrão: todas as APIs GRD_API_ retornam Success, Message e Data. Verifique Success antes de usar Data.
  • Opcionais: WIPOrderNo e ResourceName são opcionais — quando não houver valor a informar, envie "-1" no lugar.
  • CheckPoints: envie um item para cada checkpoint do checklist; itens ausentes não são apontados.
  • Valores: dentro de CheckpointValue, Checked aceita apenas 0 ou 1; CustomValue e AditionalInformation são opcionais (envie "" quando não houver).

GRD_API_VerifyChecklistStatus

Verifica se o checklist já foi preenchido no período para um ou mais recursos. Recebe uma lista de verificações (recurso + checklist + período) e devolve, para cada item, se já está preenchido (Done).

Chamada

API GRD_API_VerifyChecklistStatus

Operação de servidor invocada com um corpo JSON. Diferente das demais, o corpo é um array e a resposta também é um array (um item de retorno por item enviado).

Inputs

Payload (antes do JSON.stringify)

Lista de verificações (recurso + checklist + período):

[
  {
    "ResourceName": "10000000014 (SENSOR_D)",
    "ResourceNameWorkcenter": "1000000020 (SALA1)",
    "CheckListCode": "CHECKLIST_TEMP",
    "Period": "DAY | WEEK | MONTH"
  },
  {
    "ResourceName": "10000000015 (SENSOR_E)",
    "ResourceNameWorkcenter": "1000000020 (SALA1)",
    "CheckListCode": "CHECKLIST_TEMP",
    "Period": "DAY | WEEK | MONTH"
  }
]
const body = { Parameters: JSON.stringify(payload) };   // <- é isto que o endpoint recebe

Campos de cada item de entrada

Campo Tipo Obrigatório Descrição
ResourceName string Sim Nome do recurso (equipamento) a verificar. Ex.: "10000000014 (SENSOR_D)".
ResourceNameWorkcenter string Sim Nome do workcenter/sala do recurso. Ex.: "1000000020 (SALA1)".
CheckListCode string Sim Código do checklist a verificar.
Period string Sim Janela de verificação: DAY (dia) · WEEK (semana) · MONTH (mês).

Outputs

Resposta (JSON) — lista com o resultado de cada verificação:

[
  {
    "ResourceName": "BALANCA_A",
    "CheckListCode": "CHECKLIST_BALANCA_A",
    "Done": 0
  },
  {
    "ResourceName": "BALANCA_B",
    "CheckListCode": "CHECKLIST_BALANCA_B",
    "Done": 1
  }
]

Campos de cada item de saída

CampoTipoDescrição
ResourceNamestringRecurso verificado (eco do input).
CheckListCodestringChecklist verificado (eco do input).
Donenumber1 = checklist já preenchido no período · 0 = ainda não preenchido.

Notas

  • Entrada e saída em lote: a API recebe e retorna um array; a resposta traz um item para cada verificação enviada.
  • Período: Period define a janela em que o preenchimento é considerado válido (dia, semana ou mês corrente).
  • Sem envelope Success/Message: diferente das demais APIs, o retorno é diretamente a lista de resultados.

GRD_API_GetCheckListHistory

Recupera o histórico de checklists — devolve os checklists já apontados, com o percentual de preenchimento e o status final, filtráveis por ordem, código, recurso, usuário, período e status.

Inputs

Corpo da requisição (JSON) — filtros opcionais. Use "-1" para ignorar um filtro:

{
  "WipOrderNo": "-1",
  "CheckListCode": "-1",
  "ResourceName": "-1",
  "CreatedBy": "-1",

EndDate string (data) Não Fim do período (YYYY-MM-DD).
Status string Não Filtra pelo status final: "OK" · "NOK" · "-1" (todos).

GRD_API_GetCheckListHistoryDetail

Histórico com % de preenchimento

Lista o histórico de apontamentos de checklist (somente o cabeçalho) de uma ordem, com totais e o percentual de checkpoints marcados (Checked = 1) em cada apontamento. Usa uma CTE que agrega CHECK_POINT_HISTORY por CheckListHistoryID, extraindo $.Checked do JSON com JSON_VALUE.

Query

;WITH cteCheckPointHistory AS
(
  SELECT
    CheckListHistoryID,
    COUNT(*) AS TotalChecks,
    SUM(CAST(JSON_VALUE(Value_, '$.Checked') AS INT)) AS SumChecked,
    CAST(SUM(CAST(JSON_VALUE(Value_, '$.Checked') AS INT)) * 100.0 / COUNT(*) AS DECIMAL(5,2)) AS PercentOfTotalChecked
  FROM CHECK_POINT_HISTORY
  GROUP BY CheckListHistoryID
)
SELECT
  CheckListHistory.ID AS CheckListHistoryID,
  CheckListBase.CheckListCode,
  CheckListHistory.ResourceName,
  CheckListHistory.WipOrderNo,
  CheckListHistory.CreatedBy,
  CheckListHistory.CreatedOn,
  cte.*
FROM CHECK_LIST_HISTORY CheckListHistory
INNER JOIN cteCheckPointHistory cte ON CheckListHistory.ID = cte.CheckListHistoryID
INNER JOIN CHECK_LIST CheckListBase ON CheckListHistory.CheckListID = CheckListBase.ID
WHERE CheckListHistory.WipOrderNo = '1000000001'
ORDER BY CheckListHistory.CreatedOn

Parâmetro

Filtro Descrição
CheckListHistory.WipOrderNo Número da ordem (WIP Order) cujos apontamentos de checklist se deseja listar.

Colunas retornadas

Coluna Descrição
CheckListHistoryID ID do apontamento de checklist (CHECK_LIST_HISTORY.ID).
CheckListCode Código do checklist apontado.
ResourceName Recurso/equipamento onde o checklist foi apontado.
WipOrderNo Número da ordem vinculada ao apontamento.
CreatedBy Usuário que registrou o apontamento.
CreatedOn Data/hora do apontamento (usada na ordenação).
TotalChecks Total de checkpoints do apontamento.
SumChecked Quantidade de checkpoints marcados (Checked = 1).
PercentOfTotalChecked Percentual de preenchimento: SumChecked × 100 / TotalChecks (DECIMAL 5,2).

Notas

  • Header apenas: traz uma linha por apontamento (CHECK_LIST_HISTORY) — para o detalhe de cada resposta use a query Detalhe das respostas.
  • JSON: Value_ guarda o valor do checkpoint em JSON; JSON_VALUE(Value_, '$.Checked') extrai o flag 0/1 para agregação.
  • Percentual: PercentOfTotalChecked usa 100.0 (decimal) para evitar divisão inteira e arredonda em DECIMAL(5,2).

Detalhe das respostas

Retorna o detalhe de cada checkpoint respondido de um apontamento específico, com a descrição traduzida do checkpoint e os campos do valor (Checked, CustomValue, AditionalInformation) extraídos do JSON em CHECK_POINT_HISTORY.Value_.

Query

SELECT
  CheckListHistory.ID AS CheckListHistoryID,
  CheckListHistory.ResourceName,
  CheckListHistory.WipOrderNo,
  CheckListHistory.CreatedBy,
  CheckListHistory.CreatedOn,
  dbo.fnGetTranslation(CheckPoints.TextID, 1033) AS CheckPointDescription,
  JSON_VALUE(CheckPointHistory.Value_, '$.Checked')   AS Checked,
  JSON_VALUE(CheckPointHistory.Value_, '$.CustomValue')    AS CustomValue,
  JSON_VALUE(CheckPointHistory.Value_, '$.AditionalInformation')  AS AditionalInformation
FROM CHECK_LIST_HISTORY CheckListHistory
INNER JOIN CHECK_POINT_HISTORY CheckPointHistory ON CheckListHistory.ID = CheckPointHistory.CheckListHistoryID
LEFT JOIN CHECK_POINT CheckPoints ON CheckPointHistory.CheckPointID = CheckPoints.ID
WHERE CheckPointHistory.CheckListHistoryID = '100000004'

Parâmetro

Filtro Descrição
CheckPointHistory.CheckListHistoryID ID do apontamento de checklist (CHECK_LIST_HISTORY.ID) — o mesmo CheckListHistoryID retornado pela query de histórico.

Colunas retornadas

Coluna Descrição
CheckListHistoryID ID do apontamento de checklist.
ResourceName Recurso/equipamento do apontamento.
WipOrderNo Número da ordem vinculada.
CreatedBy Usuário que registrou o apontamento.
CreatedOn Data/hora do apontamento.
CheckPointDescription Descrição traduzida do checkpoint via dbo.fnGetTranslation (LCID 1033).

  • Detalhe por linha: uma linha por checkpoint respondido do apontamento informado.
  • LEFT JOIN: o join com CHECK_POINT é LEFT para não perder respostas cujo checkpoint base tenha sido removido — nesses casos CheckPointDescription vem NULL.

  • Filtros: ProductNo e Lot aceitam "-1" para não filtrar — combine-os (ex.: só ProductNo para ver todos os lotes do material).
  • Múltiplas linhas por lote: o mesmo lote pode aparecer em mais de uma P_Location, cada uma com sua P_Quantity.
  • Origem: os dados vêm diretamente do JDE — os campos usam o prefixo P_ conforme retornados pela integração.
